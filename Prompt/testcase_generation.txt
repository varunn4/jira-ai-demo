METHOD - follow this order before writing anything:
1. Identify the entry points the change touches: the endpoint, component, handler or job named in the ticket, matched against real names in the source above.
2. Walk the dependency map. For each entry point, note what calls it (a change here can break those callers) and what it depends on (those can fail and this must handle it).
3. Identify the state the change reads and writes: tables, caches, queues, external APIs, session or local storage.
4. Only now write test cases, each one traceable to something you identified in steps 1-3.

MANDATORY COVERAGE - a suite missing any of these is incomplete:
- Positive flow, end to end, with concrete input values.
- Field and boundary validation: empty, minimum, maximum, over-limit, wrong type, unicode, and injection-shaped input.
- Negative and error paths: rejected input, dependency failure, timeout, unauthorized, not found, conflict.
- Mid-flow abandonment: the user refreshes, navigates back, closes the tab, or loses connection partway. State exactly what state is left behind and whether it is recoverable.
- UI interaction states: button enabled/disabled, double submit, loading, retry after failure, and what the dashboard or list view shows before and after.
- Destructive actions: delete and its confirmation, cascade effects, and whether it can be undone.
- Concurrency: two users, or two tabs, performing the action simultaneously.
- Regression risk: name the specific existing behaviour this change could break, taken from the callers in the dependency map.

HARD RULES:
- Generate a MINIMUM of 8 and a MAXIMUM of 10 test cases. Fewer than 8 means the change has not been thought through; more than 10 means padding.
- Ground every case in a real name from the context above: a file, function, endpoint, component, table or column. A test case that names nothing real is worthless.
- Never restate the ticket description as a test case. "Verify the feature works as described" is a failed test case.
- Where the context does not cover an area, say so explicitly in a "Coverage gaps" section at the end. Never invent a component, file or function that does not appear above.
- Every case must be executable by someone who has not read the ticket: concrete inputs, concrete expected results. Never "verify it works correctly".
- Do not duplicate coverage that RELATED WORK shows already exists. Reference it and focus on what is new.

FORMAT each test case as:
- ID and a specific title
- Area: the module, file or endpoint it covers
- Preconditions: the data and system state required
- Steps: numbered, concrete, with actual values
- Expected Result: observable and specific
- Priority: P0-P3
- Regression risk: what existing behaviour this protects, or "none"

Close with a "Coverage gaps" section listing what you could not verify from the supplied context and what would be needed to cover it.

OUTPUT:
- Clean markdown. No markdown tables if the output is bound for Slack.
- EMOJI PROHIBITION: Emojis are strictly prohibited. Never use any emojis, icons, or pictorial symbols.
